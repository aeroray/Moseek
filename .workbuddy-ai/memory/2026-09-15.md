## 直播页面黑屏排查与修复

- 排查范围：`src/features/live/live-view.tsx`、`src/features/player/media-player.tsx`、`src/lib/tauri.ts`、
  `src-tauri/src/{live,resolver,policy}.rs`、`src-tauri/tauri.conf.json`，并结合本地 SQLite

  已用 Chromium 做三组对照实验确认（原 CSP 失败 / 无 CSP 成功 / 加 `worker-src 'self' blob:` 成功）。
- 修复：`tauri.conf.json` CSP 增加 `worker-src 'self' blob:`；
  `media-player.tsx` 把 HLS 实例创建抽成可重建流程，遇到 `demuxerWorker` 的 `internalException`

## rustc ICE（exit code 101）排查与修复

## 黑屏真正根因：React StrictMode 双重挂载摧毁播放器 DOM

- 用户反馈修复后仍黑屏，并给出诊断面板导出。关键读数：`readyState 4`、`640×360`、
  `paused=false`、`buffered 48.1–54.0s`、`MediaSource open`、转封装线程可用、解码支持齐全——
  **媒体其实在正常播放**，但 `播放状态：等待播放`，且事件时间线里**没有 `play` / `playing`**。
  同时 `创建 hls.js 实例` 出现了两次，暴露了 StrictMode 双重挂载。
- 复现：本地用 mise 的 ffmpeg 生成 640×360 H.264+AAC 的 HLS（去掉 ENDLIST 当作直播），
  经 Vite 提供（注意分片不能叫 `.ts`，否则被 Vite 当 TypeScript 编译而返回 500），
  在 Chromium 里跑同一份 `MediaPlayer`。结论确凿：
  - 不包 `<StrictMode>`：`plyr/wrapper/video` 均 512×288，`playing` 正常触发，画面可见。
  - 包 `<StrictMode>`：`plyr=缺失 wrapper=缺失`，播放器 DOM 被摧毁，`networkState=0`，
    播放从未启动，截图就是**纯黑 + 转圈**。
- 根因：Plyr 会把 `<video>` 包进自己的 DOM，hls.js 会给它挂 MediaSource，二者都不能在同一元素上
  构造两次；StrictMode 在开发模式下 mount → unmount → remount，导致两个库被构造两遍，
  Plyr 的 wrapper 与媒体事件监听最终被拆掉。
- 修复（`media-player.tsx`）：新增 `scheduleBoot(task)`，把**首次**构造推迟一个宏任务，
  卸载时 `clearTimeout` 取消，从而每次真实挂载只构造一次；`createHlsInstance` 重命名为
  `createHlsInstanceNow`（保持原缩进不动），重启/重试路径仍同步重建。
- 验证（StrictMode 下）：`plyr/wrapper/video` 恢复 512×288、`buffered=12.0-24.0`、`转圈=false`、
  `statuses=playing`，截图显示出 ffmpeg 测试图案（不再黑屏）。
- 附带：诊断面板「媒体元素」一行补上 `currentTime`（原来缺这个关键读数）。
- 按用户要求，`ScrollArea` 恢复默认 `type`（不再强制 `always`）；已在 decisions 里记下
  Radix 默认 `"hover"` 导致静止时看不到滚动条这一项目级现象，供后续决策。
- 验证：pnpm typecheck / lint / test（27 passed）/ build 全部通过。

     而同步草稿的 effect 依赖 `[activeConfigId, configBaseUrl, rawConfig]`，
     于是 effect 在批次提交后重跑并执行 `setImportText(rawConfig)`，把刚取到的文本覆盖成当前文档内容。
  4. `handleLocalFile` 因 `await file.text()` 在 effect 之后才 resolve，反而没受影响——这也解释了为什么只有远程导入出问题。
- 修复：把 `configBaseUrl` 从该 effect 的依赖中移除（只保留 `activeConfigId` / `rawConfig`），并写明原因。
  修复后 `importText` 在"获取配置 → 解析配置"之间不会被任何自动逻辑改写。
- 验证：pnpm typecheck / lint / test（35 passed）/ build 全部通过。
- 未替用户改数据：文档 9 仍是错误副本，需在界面里删除后重新导入（数据库位于 %APPDATA%，属应用数据，不擅自修改）。
- 待办建议（未实现）：导入时若与已有文档内容完全相同，给出提示，避免"又出现一份一样的"。

## 为导入覆盖 bug 补回归防护

- 该 bug 的机制是 effect 依赖数组多了一项（`configBaseUrl`），**加回去不会有任何编译或 lint 报错**
  （项目装了 `eslint-plugin-react-hooks` 但没启用，且 exhaustive-deps 只查"缺少依赖"、不查"多余依赖"），
  所以只靠注释不够。
- 做法：把规则抽成 `src/features/config/config-drafts.ts` 的 `shouldResetDrafts(previous, next)`，
  用 `draftSourceRef` 守卫 effect——文档身份或内容变化才重置草稿，`configBaseUrl` 只作为输入携带、**不参与比较**。
  这样"某个输入必须被忽略"这条不变式被显式表达，并可独立单测（不依赖渲染 ConfigCenter）。
- `config-drafts.test.ts` 4 例，第一条直接复现 bug 输入（同文档同内容、仅 base url 变化 → 不得重置）。
- **变异测试验证过测试有效性**：把 `configBaseUrl` 加回比较后，正是那一条用例失败、其余 3 条通过；
  随后已恢复实现并复测。
- 验证：pnpm typecheck / lint / test（39 passed，原 35 + 新 4）/ build 全部通过。

## 导入重复检测（把选择权交给用户）

- 用户需求：导入时若发现"已经有了"，让用户自己选 **跳过** 还是 **继续导入**；
  并特别指出场景——某份配置导入后被用户裁剪过（删掉失效资源），之后再导入原始版本，
  **文本内容已经不同**，所以单纯比对内容会漏掉。且再次导入的地址可能不同，比对 URL 也不够。
- 方案：比对**源 key 集合的包含关系**，这正好命中"裁剪"场景（裁剪后的集合是原版的子集）。
  新增 `ConfigDuplicateMatch` + `find_config_duplicate` 命令（`config/commands.rs` + `storage.rs`），
  匹配优先级：`identical`（文本相同）→ `derived`（一方源集合包含另一方，取重合最多者）
  → `same-origin`（同一导入地址）。返回双方源数与重合数，由前端组装文案。
  匹配刻意放宽：用户是"被询问"而不是"被阻止"，误报代价是一次点击，漏报代价是静默产生重复配置。
- 前端：`config-duplicate.ts` 的 `describeDuplicateMatch` 组装文案（5 例单测，含两个裁剪方向）；
  `handleParse` 改为"解析 → 查重 → 让用户选择"，对话框内显示重复说明 + 底部切换为「跳过 / 继续导入」；
  「跳过」不落库并提示未创建；关闭对话框时清空查重状态。
- Rust 测试 6 例（相同内容、双向裁剪、取重合最多、同地址、无关配置保持安静）。
- **真实数据验证**（临时探针，跑完即删，只读打开用户的 moseek.sqlite3）：
  文档 2（237 源）原样导入 → `identical`；裁剪到 118 源后再导入原版 → `derived`，双方计数正确。
  注：Rust `String::len()` 是字节数，与 Python 的字符数不同（74910 字符 = 82384 字节），非数据不一致。
- 验证：cargo test（37 passed，原 31 + 新 6）/ clippy / fmt --check，pnpm typecheck / lint / test（44 passed，原 39 + 新 5）/ build 全部通过。
