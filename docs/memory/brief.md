# Project Brief

拾影 (Shiying / Moseek) 是一个面向 Windows 优先的桌面端影视资源聚合工作台与多源流媒体播放器，Slogan 为「万千影视，一拾即得」。它连接并整合多元化的视听生态：支持透明 TVBox/CatVod 配置导入、普通 CMS/直播源探测分类、影视聚合检索与多线路秒开、HLS 原生硬件加速直播、以及受沙盒保护的安全执行边界。

前端采用 React 19 + Vite + TypeScript + Tailwind CSS v4 + 精致紧凑的「极光黑曜 (Cinematic Obsidian)」黑曜石暗色影院级 UI 设计规范，搭配 Tauri 2 作为桌面壳体与 Rust 高性能媒体/网络/存储层。

播放地址解析的既定顺序：直链 → **扫描播放页内嵌的媒体地址**（源自己的主机，不执行脚本、不经第三方）→ 并发的第三方解析服务兜底。影视库进入观看页只预加载与呈现播放器，**不自动播放**，且「足迹」只在真正开始播放后写入。

窗口标题为三段式：`Moseek · 拾影 · 万千影视，一拾即得`（`tauri.conf.json` 与 `index.html` 必须一致）。「系统设置」页与「配置中心」共用同一套版式：`max-w-6xl` 居中列、固定头部、带图标的标签行、每标签一张卡（卡片按内容高度、滚动在标签内）。

清除类的破坏性操作统一走 `src/components/clear-records-dialog.tsx`（足迹 / 我的收藏 / 系统设置三处共用）：默认全选的复选框 + 随选择范围变化的确认按钮文字。store 里 `clearHistory(kind?)` 与 `clearFavorites(kind?)` 对称——影视与电视直播各自是独立字段，**传 kind 只清那一边**。

配置采用**合并**模型：删除一个源只把它从当前配置（原始文本 + 源快照）移除，**不记录「这个源是用户不要的」**，因此之后导入的文件里若仍有该源，它会作为新源被加回来；导入时同一源仍在则跳过、不产生第二行。清理源时要同时过滤 `favorites`、`liveFavorites` 与 `history`（三者都以 sourceKey 关联）。

配置中心里**列表计数与原文条数不必然相等**：没有 `url`/`api` 的条目（如只有嵌套 `channels` 的 TVBox 重定向项）被解析器判为 `invalid`，不进列表。列表显示的是**可用（`enabled && supported`）**的源数。

配置中心只有**三个**标签页：源列表 / 适配器 / 原始配置。「解析报告」与后来的「源健康」**都已删除**（`config-report.ts` 不再存在）——用户判定它没有实际价值。

**导入对话框里没有「配置名称」字段。** 导入是**合并进中心配置**的，所以用户输入的名字当场就被丢弃（文档保留中心配置自己的名字）。**要一个用不上的值比不要更糟**：它暗示导入会新建一份独立配置，而这正是这个页面已经取消的模型。

**源列表每行的第二行显示地址，不显示 `source.key`。** 原本是 `{source.key} · 直播源`，而实测用户自己的配置里有三个直播源的 key 是 `-7`/`-8`/`-9`——那是**发布方自己编的数组下标**，读者无从理解。地址才是人用来辨认一个源的东西；没有地址时退回显示类型（用户的配置里确实有一个无地址条目）。

**页面级状态横幅已改为 toast。** 它原本钉在列表下方、直到下一次操作才被替换——把「一时的结果」做成常驻记录，还占着列表自己页脚的位置。现在统一走页面本来就在用的 toast 通道（测速、删除也用）。**实现上是一个 `useEffect` 观察 `parseState`**，而不是改写 37 个调用点；对话框打开期间只标记为「已处理」不弹 toast（那时消息属于导入框内、就在被导入的文本旁边），所以关掉对话框不会把已经展示过的消息再弹一遍。

**多仓列表支持「全部合并导入」。** 18 个地址否则就是 18 次往返对话框，而编辑器一次只装一份文档，「全选」原本无法表达。按钮会取回每个地址、在内存里**合并成一份文档**、再走普通导入路径提交——**一次写入，不是十八次**。两个刻意的决定：**失败是收集而不是抛出**（实测 18 个里有 1 个域名已失效；因为一个死链放弃整批，用户会既拿不到东西也不知道是哪个坏了，所以能用的照常合并、不能用的点名），以及**批量为不设 base URL**（18 个地址通常在不同主机上，没有哪个目录能让相对路径正确解析，随便挑一个会静默改掉其他地址）。

`Empty` 自带 `flex-1`，但它原本放在普通块级容器里，**`flex-1` 在块级里不起作用**，所以虚线框只包住自身内容、在卡片底边上方留出空隙。外层改为撑满剩余高度的 flex 列，`flex-1` 才有意义。**实测（真实浏览器）**：虚线框底边距内容区底边 16px、距卡片底边 17px（这 16px 就是 `p-4` 的内边距），即虚线框确实贴到了容器底。

**导入对话框的卡顿不是编辑器造成的，是「源列表表格跟着每次按键重渲染」。** 用户以为是编辑器，实测推翻了：对话框里的 CodeMirror 每敲一个字符，在**挂载 358 行源列表**时中位数 **30ms**，把同一张表筛到只剩 1 行时中位数 **7ms**——同一个对话框、编辑器里同一份文档，只有旁边那张表不同。根因是 `importText` 和表格同住在 `ConfigCenter` 里，所以每次按键都重渲染 **18622 个 DOM 节点**。修法是把表格抽成 `SourceTable` 并用 `React.memo` 包起来，**同时把 props 变成引用稳定的**（`filteredSources` 本来就是 `useMemo`；`handleToggleSource`/`performRemoveSources`/`handleRemoveSources`/`handleTestSource`/`handleCancelTestSource`/`handleCancelTestAll` 原本是每次渲染都新建的普通函数，全部改成 `useCallback`）——**不稳定的 props 会让 `memo` 变成摆设：看起来修了，实际每次按键照旧重渲染**。**实测修复后：满 358 行挂载下中位数 7ms**，与筛到 1 行时持平，DOM 节点数不变（18709），说明是渲染隔离而不是把表做小了。

**但「打字时的重渲染」和「弹窗打开/关闭」是两笔不同的开销——`memo` 管不了后者。** 用户第二次反馈仍然卡，并猜到是源列表没做虚拟列表；实测他猜对了。同样开关弹窗、**只改旁边表格挂载的行数**：满表时打开 **270ms（一条 269ms 长任务）**、关闭 **101ms（100+144ms 长任务）**；筛到 1 行时打开 **22ms**、关闭 **7ms**，**一条长任务都没有**。CPU profile 归因到 `eq @ config-center` 123ms + `removeChild` 96ms + `focus` 97ms，即 React **挂载/卸载整棵表格 DOM 树**。**`memo` 只能阻止不必要的重渲染，而打开弹窗无论如何都要挂载一次表格**，所以只有「不挂载屏幕外的行」才能解决。改用 `@tanstack/react-virtual`（用户要求优先用现成依赖），实测打开 **48ms**、关闭 **22ms**，**两次都零长任务**，挂载行数 358 → **19**，DOM 节点 18623 → **1022**。`ScrollArea` 因此加了 `viewportRef`：Radix 滚动的是内层 `Viewport` 而不是 `Root`，拿 `Root` 的 ref 当滚动元素是错的；暴露 ref 也好过让调用方用 `querySelector` 去够内部结构。

**虚拟列表极易「看起来变快了、其实悄悄坏了」，所以下面每一条都在真实浏览器里对着真实 358 行配置验过，而不是假设**：滚动条仍描述整个列表（用占位行撑高，实测 `scrollHeight` 19006 对全高 18974；**不能给 `tbody` 加 padding**，各浏览器布局不一致）；**滚到中间相邻可见行的盒子首尾相接、缝隙列表为空**（不会出现空白带）；**滚到最底时最后一行正好贴在视口底部（差 0px）且是真正的最后一个源**（窗口差一个就会在这里暴露）；**行内操作作用于它画在的那一行**（滚动后同一行的测试/启用/删除三个按钮都指向该行自己的源名——虚拟列表复用 DOM 最容易让处理器跟错记录）；粘性表头仍然粘住、页面仍然不滚动。

**jsdom 无法虚拟化，这一点决定了设计。** 实测：jsdom 里 500px 高的滚动容器 `clientHeight` 是 **0**，且本项目的 `ResizeObserver` 桩**从不触发回调**。所以按测量驱动的虚拟列表在 jsdom 里会**一行都不渲染**，把现有每条表格断言都变成「找不到行」，而其实什么都没坏。因此回退是显式的、且是**真实测量而非 `typeof window` 判断**：`hasLayoutEngine()` 插入一个 10px 元素再读回来，没有布局引擎时整表渲染——这正是测试拿到的结果，也是 ~130 条既有表格测试原样通过的原因；并有一条测试断言该探针在 jsdom 下返回 false，防止它被悄悄反转。

**`configDocumentCache` 是 localStorage 配额报错的根因，而且它在「增长」。** 实测持久化对象 **4467KB / 5120KB 配额（87%）**，其中 cache 占 **2233KB**——它把每份文档的 `rawConfig`/`normalizedConfig`/`sources` 又存了一遍，而顶层已经存了同样三样。更糟的是**每次保存都会产生新的文档 id，而 cache 只增不减**（`setConfigDocument` 是展开追加，只有 `removeConfigDocument` 会删），自动保存意味着**每次编辑都可能再堆一份 2233KB**，两份就 6700KB 直接爆配额。修法是 cache 只持久化顶层没有的东西（名字、base URL、计数），且只留活动文档：**4467KB → 2233KB，再存十次增加 0KB**。另外那个异常原本被 catch 成「需要修正配置」——**把浏览器存储满了说成配置有问题**。

**多仓「全部合并导入」是并发的**：显示 `N / 总数`，**计数在每次取回完成时递增**（并发在飞时这是唯一真实的进度数字），且批量运行期间选择框保持打开。串行改并发的原因是可测量的：18 个地址分布在 18 个不同主机上，串行要付 **18 次往返 + 18 次 TLS 握手**的总和，而它们彼此毫无依赖（各自取回、各自修复、各自成文档，只有最后的合并需要全部到齐）——串行唯一换来的就是更长的等待。用**有界**工作池（`IMPORT_CONCURRENCY = 4`，与测速同一个宽度）而不是 `Promise.all` 全部并发：18 个还行，100 个就不是了，而后端只约束单个请求、不约束批次。**结果按原顺序保留**，所以合并后的源顺序仍与用户看到的列表一致。

**源列表的列会随滚动左右移动——这是虚拟列表引入的回归，根因是 `table-layout: auto`。** 浏览器按**当前挂载的行**推导列宽，而虚拟列表会在滚动时改变挂载集合，所以列宽被反复重算。实测六个滚动位置：第一列宽度走 **494 → 333 → 348 → 559 → 333 → 532px**，第二列左边缘走 **679 → 518 → 533 → 744 → 518 → 717px**。改成 `table-fixed` 并显式声明各列宽度后，六个位置的左边缘与宽度**完全一致（各只有 1 种取值）**。**虚拟列表的列宽必须与挂载了哪些行无关**，否则「滚动时表格在动」是必然的。

**「清理不可用」的卡顿是 O(被删数 × 条目数) 的嵌套扫描，实测 release 下 1979ms。** `entry_identity`（内部含 `Url::parse`，还可能解析 JSON）原本在匹配循环的最内层被调用，删 1347 条 × 1701 条 ≈ 230 万次昂贵调用；可追溯性检查是同样的形状。改为**每个条目只算一次身份**并建哈希索引后：**1979ms → 17.5ms（113 倍）**。因为这是 113 倍的改写，「更快但算错」比「慢但对」更糟，所以**用从 git 取出的原实现做了逐字节等价验证：12 组（用例 × 文本）输出完全相同**；并保留 4 条测试钉住排序规则（精确 key 优先于更早的同名匹配、无地址条目不按身份匹配、无法追溯的文本不做修剪、大小写与末尾斜杠折叠）。Rust 命令同时从同步改为 `async` + `spawn_blocking`：**同步的 `#[tauri::command]` 跑在主线程上**，重写期间窗口完全无响应；为此 `AppDatabase` 的 `Mutex` 包进了 `Arc`（`spawn_blocking` 需要 `'static`）。

**「全部测速」是「主按钮 + 作用域菜单」，且菜单用官网原版的 `Button + DropdownMenu`——最初用 `Select` 是错的，用户一眼看出「跟官网原版不一样」。** 用户要能选「只测未测过的」。官方 `ButtonGroup` 示例的搭配就是 `DropdownMenu`（`DropdownMenuTrigger asChild` 包一个 `Button`，里面放 `ChevronDownIcon`），而**本项目当时根本没装 `dropdown-menu`**，我塞了个 `Select` 进去。差别是本质的：**`Select` 是选择器**——菜单以 `item-aligned` **盖在 trigger 上**打开、当前值旁带对勾、**再次选中当前项不触发 `onValueChange`**；**`DropdownMenu` 是动作列表**——菜单**落在 trigger 下方**、每一项每次都触发。所以「全部测速」在 `Select` 下作为重复动作不可达（这才是当初要多一个常驻主按钮的真正原因），而在菜单里两个作用域都是普通的可重复动作。**实测真实构建产物**：菜单 `opensBelowTrigger: true`、右边缘对齐（误差 <2px）、`overlapsTrigger: false`、两项文本为「全部测速（4）」「只测未测过的（1）」。**去掉 `testScope` 状态**：动作菜单没有「当前选中值」可记。**顺带删掉了 `SelectValue` 那一整套 `sr-only`/`data-slot` 变通**——`Button` 原样渲染子节点，没有要藏的东西。注意 `npx shadcn add` 在本项目会把文件写到字面目录 `@\components\ui\`（`@/` 没被展开），要手动搬到 `src/components/ui/`。

**必须纠正一条记错因果的旧结论：打开 Radix 浮层「把事件循环占满」是错的，真正的代价是 popper 的碰撞检测，而且是 jsdom 独有的。** 旧记录说「`DropdownMenu` 打开时 25ms 定时器实测耗时 24766ms、关掉立刻恢复」，并据此换成了 `Select`。这次**逐项重测**：**菜单打开状态下 25ms 定时器只花 25.0ms**（关闭时 37.7ms，甚至更慢）——打开状态根本不贵；那 ~19s 花在**别处**。用「`Select` 换定位」做对照实验（各 3 个测试）：`Select` + `item-aligned` **193ms**、`Select` + `position="popper"` **53183ms**、`DropdownMenu` **51775ms**——**代价只跟 popper 有关，与是哪个组件无关**。定位到具体中间件：**`avoidCollisions={false}` 让 51775ms → 7773ms，5 个测试稳定在 ~3.2s/个（原来 ~19.5s/个，约 6 倍）**；贵的是 `shift`/`flip` 为检测溢出而遍历**每一个 clipping ancestor**——在 jsdom 的零布局树里毫无意义，而这个菜单挂在工具栏上、下方整片是源列表，本来也无处可避。**已证伪的假设**（都实测过、都没用）：rAF 桩（含完全不回调的死桩）、`pretendToBeVisual: false`、`updatePositionStrategy="optimized"`、`modal={false}`、测试里显式 close/unmount——**且计时显示开销落在 `afterEach` 之后到下一个 `beforeEach` 之间**，即运行时的环境拆除，不是我们的代码。**注意这次差点又一次「只看数字就下结论」**：第一次测「打开状态」得到 26.6ms（比关闭还快），是因为菜单**根本没打开**（`findByRole("menu")` 抛错才发现）；加上「先断言菜单真的开了」之后才得到真实数字。**同理，`findByRole` 在这个菜单上是陷阱**：节点在按键后 **76ms** 就在 DOM 里，而 act 包裹的 `findByRole` 查同一个节点 **19.5s 才返回**——所以相关测试一律用**同步查询**。

**官网组件必须按本项目的设计语言重新上色——照抄 registry 默认值会「跟现有设计不一样」，用户一眼就看得出来。** 用户原话：「它的样式希望能和现有软件的设计语言保持一致」。**根因是 registry 的默认尺度不是本项目的尺度**：`dropdown-menu` 出厂是 shadcn 基础尺寸（`text-sm`/`py-1.5`/`rounded-sm`/`shadow-md`/`focus:bg-accent`/`size-4` 图标），而本项目所有浮层都是**紧凑 + 模糊**的（`text-xs`/`py-1`/`rounded`/`shadow-xl backdrop-blur-md`/`border-border/90`，**选中态是金色 `focus:bg-primary/15 focus:text-primary`**，图标 `size-3.5`）。**最刺眼的是 `shadow-md`**：在极光黑曜背景上小阴影读起来像一块平贴的方块，所以 `select`/`dialog`/`toast`/`sheet` 全都用 `shadow-xl`/`shadow-2xl` + `backdrop-blur`。**改法是把 `select.tsx` 当唯一参照**（它是最贴近的同类：都是从控件上垂下来的单行选项浮层），并把面板与行样式提成 `menuSurface`/`menuItem` 两个常量，让根菜单与子菜单无法各自漂移。**验证方法是 A/B 计算样式对比而不是眼看**——在同一个页面里同时打开本项目的 `Select`（适配器页的「筛选适配器」）和新的测速菜单，逐项读 `getComputedStyle`：面板 radius **6px = 6px**、背景 **rgb(17,20,27) 相同**、边框 1px 7% 白相同、阴影 `0 20px 25px` 相同、`backdrop-filter: blur(12px)` 相同、行 radius **4px = 4px**、字号 **12px = 12px**、行高 **24px = 24px**、hover 背景 **`oklab(0.77…) / 0.15` 相同**。唯一差异是 `Select` 行右侧多 20px 内边距（`4px 28px 4px 8px` vs `4px 8px`）——那是留给它尾部对勾的位置，菜单没有对勾。**教训：引入官方组件时要问「这个项目的同类浮层长什么样」，而不是「registry 默认长什么样」。**

**测速「失败但开关没关」——用户第二轮明确推翻了上一轮的方案：「无论是请求失败还是连不上，就当做测试失败就行了……我们肯定直接把它当做不可用的东西清除掉」。** 上一轮我按「保留安全规则、只修文案」做（网络层失败不关开关，另立「连接失败」状态与分面）。**用户要的是更简单的规则，而且理由充分**：连不上或请求失败就代表那个源没用，留着它反而会被当作可用源出现在影视库里——这正是他最初看到并反对的现象；判断错的代价也有界，开关点一下就回来了。所以**整条「传输层失败」概念被删除**：`cms::is_transport_failure`（Rust）、`src/lib/transport-failure.ts`、`unreachable` 分面、状态列的「连接失败」与连接测试列的「连不上」全部移除，`nextEnabledAfterTest` 与 `storage::set_source_test_in_connection` 都简化为 **`failed || empty` 就关**，「清理不可用」也照此把连不上的源计入。**屏幕上不再有两种失败的说法**——一个没有任何东西依据的标签只是同一件事的第二种写法。**实测真实构建产物**：连不上的源（超时）从 待测试/开关开 → **测试失败/开关关**，toast 显示「已自动关闭该源的启用开关」，`清理不可用` **1 → 2**，控制台零错误。**这也让「两列说法不一致」这个隐患自然消失**：以前状态列写「连接失败」而开关不动，本身就是一种需要解释的状态。

**「未执行」这个状态本身是错的，用户一眼看出它误导：「既然它的地址不是可以请求的 HTTP 地址，没法测试的话，把它当做无效或不可用的源来处理不就行了吗？这样会让用户觉得这是一个可用的源。」——他两处判断都用真实数据证实了。** 用作者的真实数据库（`%APPDATA%\com.moseek.desktop\moseek.sqlite3`，98 个源）核对：**19 个源处于这个状态，全部是 `live` 且地址是相对路径或裸标记**（`./FM.json`、`./lib/tv/ipv6.m3u` ×11 个 `url`，`./py/kzb.py` ×3 个 `api`，外加 `yqk`、`csp_MQiTV`、`直播链接自定义`），`testStatus` 全是 `blocked`。**根因是 `getAdapterProfile` 的 live 分支无条件返回 `builtin-live`/`enabled`**——它回答的是「哪段代码会处理它」，对任何 live 源都答「直播适配器」，于是 `isTestableLiveSource` 说可以测，行上就给了**测试按钮和启用开关**；测试跑起来必然返回 `blocked`，状态列就渲染**未执行**：一个连请求都发不出的地址，被呈现成「只是还没试过」。**修法是把「地址能不能取」放进注册表本身**（`isFetchableLiveUrl`，镜像 Rust 的 `is_fetchable_live_url`），不可取时归到 `private-protocol` 档（`needs-adapter`，其 reason 正是解析器给这类源的原文「需要单独适配器，当前不执行」）。**注意必须放在注册表而不是只放在 `isTestableLiveSource` 里**：状态列对不可测源的回退正是 `getAdapterProfile(...).execution`，适配器页也按它计数——**只改一处会让状态列渲染「可执行」紧挨着适配器列的「没有可用适配器」，一行自相矛盾**（这正是本项目修过的同一类 bug，浏览器实测第一版就复现了）。**实测真实构建产物**：两行从「可执行/有测试按钮/有开关」变为 **无法适配 / 私有协议适配器 / 无法测试 / 开关是「—」**，默认的「可执行」筛选不再包含它们，筛选计数 可执行 2 · 无法适配 2，控制台零错误。

**用户说「这些源都是一些相对地址，应该是可以修复好的」——也对，而且原来的修复代码漏掉了唯一需要它的那个集合。** `absolutizeRelativeSites` 只重写 `raw.sites`；实测 41 个 `sites` 条目里**有 0 个**相对地址，而 45 个 `lives` 条目里有 **14 个**。**唯一需要修的集合正是它不碰的那个**，所以 `./FM.json` 原样穿过每一次合并，永远取不到。live 条目的地址键是 `url`（部分是 `api`），已一并处理。**并且验证了「可修复」不是猜测**：这些相对路径来自多仓列表里的子配置（`SVIP📚在线`），按**该子配置自己的 URL** 解析后，`./FM.json` 返回真实播放列表（`电台,#genre#` / `Soft Rock,https://stream.revma.ihrhls.com/...`）。**同时必须避开的坑：多仓导入时每个条目的 URL 在抓取那一刻才知道，合并后只剩一个基址**——所以现在在抓取循环里就地绝对化（`absolutizeRelativeSites(raw, entry.url)`），否则那份信息永久丢失。**反向也测了**：`yqk`/`csp_MQiTV`/`直播链接自定义` 是适配器解析的名字而不是路径，绝不拼接（否则会凭空造出 `http://host/yqk`，让不可用源看起来可修）。**两个修复都做了变异验证**：注掉 `lives` 重写 → 只有那条新测试失败；注掉注册表的地址判断 → 只有那条新测试失败。

**顺带证伪了一个看起来很漂亮的错误结论，值得记：那些 200 响应什么都不能证明。** 用 Python 探测解析后的地址时，`http://xmbjm.fh4u.org/lib/iptv.m3u` 返回 **200**，我差点据此断言「文件存在、只是没被解析」。**做对照实验才发现：同一个主机对任意路径都返回 200 + 一段 JS AES 反爬挑战**（`http://xmbjm.fh4u.org/lib/definitely-not-here-9f3a.m3u` 同样 200）。所以那批 200 是**无意义的信号**——真正能证明修复有效的是按**子配置自己的基址**取回的内容（真实的 `电台,#genre#` 播放列表）。**「先证明前提成立」这条规矩又一次生效：没有那个对照，我会以「地址是通的」发货。**

**播放器「一直显示正在确认可以播放」的根因是 `fetch_media_bytes` 用了文档客户端，而它的超时是整段交换的 15 秒——不是「这个源坏了」，是我们的截止时间错了。** 用户给的源（🎥┃豪华┃资源）自测**全项通过**（含 playback），却能无限转圈。用**应用自己的函数**跑真实分片：**6 个里失败 3 个，且都精确停在 15010ms**，报的还是一句极具误导性的 `error decoding response body`。**根因链是两段**：① 该源的两条线路里**第一条是 HTML 播放页、第二条才是真 `.m3u8`**（实测 `text/html` vs `application/vnd.apple.mpegurl`），而播放器默认取 `playLines[0]`——**但这一条我最初猜错了**：`scan_episode_page` 其实**正确地**把 HTML 页扫成了 `.m3u8`（`adapter_id=page-scan`），所以我原本准备写的「扫描器坏了」是错的，**是 `fetch_media_resource` 拿到了正确的解析结果却仍然去取原始地址**。② 真正的杀手是**分片本身**：真实分片 2.5MiB、**实测单个要 48 秒（54 KiB/s）**，而 `fetch_media_bytes` 走 `ClientMode::Buffered`（`builder.timeout(15s)`）。**改走 `ClientMode::Streaming`（只约束两次读取之间的间隔，`STREAM_READ_TIMEOUT`）后实测 0/6 失败**，最慢的一个 26 秒——**那一个正是旧的 15 秒预算必然杀掉、且永远不可能成功的情况**。**这个改动必须保住「主机静默就失败」这条真实约束**，而它确实保住了：`Streaming` 仍有 per-read 截止时间，且上游调用方各有自己的上限（直播探测外面套 `tokio::time::timeout`，播放器加载器自己有 60 秒）。**回归用既有的直播 FLV 网络测试一起验证**（同一个函数被直播路径共用），7 条 ignored 网络测试全绿。

**「暂无可播放的剧集」是解析器读不出剧集，而页面明明有 29 集——两个独立的错叠在一起。** 用户给的第二个源（雷蒙影视 | 🍚哆啦(XBPQ)）自测里 `playback: empty`。**用真实页面跑真实解析器：`parse_play_lines` 返回 0 行**，而同一个页面的 `播放数组` 切片里**确实有 29 个剧集锚点**。两个根因：① **`播放数组` 和 `播放列表` 是「容器」与「容器里的元素」两级，而代码把顺序用反了**——先按元素切，得到的片段里**不再含有容器标记**，第二步自然什么都匹配不到（这一点有专门的测试钉住：正确嵌套得 29，反向嵌套得 0）。② **`播放链接` 这个键在结构体里根本没有字段**，落进了 `extra_keys`（解析了但从不读）；而这个方言的 `播放列表 = <a&&a>` **故意切在两个锚点之间**，所以片段里**没有 `href`**，地址只能从 `播放链接 = href="&&"` 取。**两个错各自单独就足以产出 0 行。** 修完实测**真实页面解析出 29 集**（并留了一条 ignored 网络测试跑线上页面）。

**「采集集合」的封面缺失、剧集闪烁、线路迟到是同一个根因：封面补取（cover retry）把 http-extension 适配器排除在外了。** 用真实 API 量出来的差别是决定性的：**`ac=list` 返回 20 条里 0 条有 `vod_pic`、0 条有 `vod_play_url`；`ac=detail` 返回 20/20 两者都有**。而目录页拿到的就是 `list`——**所以封面是空的，且每一行的 `playLines` 也是空的**；进详情页时那一次 `get_detail` 才把线路补上，于是「先显示没有剧集 → 一闪 → 加载 → 能播了」，右栏线路也是「先空、然后突然刷出来」。**排除的理由（「扩展源自己声明参数」）是把两件事混为一谈**：声明参数不等于声明 `ac`——这个源的 `ext` 就是标量 `"0"`，**什么都没声明**，于是默默继承了 `ac=list`。修法是让重试走**同一个适配器**（新增 `catalog_params`，把 `ac` 作为参数传入，扩展源仍套用自己的 `ext` 覆盖），而不是继续跳过它。**实测线上：20/20 封面、20/20 线路、32 个分类全部保住**（分类来自 `list`，详情页一个都没有，所以合并而非替换）。

**用户说「可能是你没有加入 loading 状态」——这个判断也对，而且是独立于上面那个根因的第二处缺陷。** 播放页原先**无法区分「源什么都没给」和「答案还在路上」**，所以整个往返期间都渲染空状态。这不是「采集集合」独有的：**任何目录行不带线路的源都会这样**。加了 `isDetailLoading`，并把「空状态」当作一个**关于源的断言**——在答案到达之前不作断言（播放区和右栏各一处，右栏标题也从会立刻被推翻的「0 线路 · 0 集」改成「正在获取…」）。**真实浏览器实测（真实构建产物 + 伪造 Tauri 桥，目录行按真实的 slim 形状喂入）**：0–1200ms 显示「正在获取剧集… / 正在获取播放线路…」，1500ms 起直接进入「正在确认可以播放…」，**`sawEmptyClaim: false`、`sawLoadingState: true`、控制台零错误**——空状态在整个过程中**一次都没出现**。同一轮还验证了封面：网格里两张海报 `complete: true`、179×268、4 张样式表已加载。

**用户截图里那 56 个「TV-…资源」不是作品，是这个聚合源自己的成员站点，而它们被当成作品渲染了——`vod_tag: "folder"` 这个字段我们根本没建模。** 症状是「列表全是奇怪的名字、没有封面，但点进去有作品名」。**决定性证据是穷举出来的**：该源广告了 `type_id` 1..32 的分类，但 **`t=1` 返回的正好是 56 条 `TV-无水印资源` / `TV-电影天堂资源` / `TV-量子资源`…**（与截图的「56 部」完全一致），每条都是 `{"vod_id":"0-0","vod_name":"TV-无水印资源","vod_tag":"folder"}`——**没有封面、没有播放地址**。`t=2` 是 23 条同类（`AV-…`），**`t=6` 起才是真作品**。所以 `t` 在这套脚本里既当分类又当站点列表，前两个 id 被站点列表占用。修法是**把 `vod_tag: folder` 当作它字面说的东西**：这类行不进作品列表；并且**整页都是 folder 时把 `total` 归零**（否则会出现「0 张卡片顶着 56 部」——`total` 是源对整个结果集的声明，但一个只剩 folder 的页面不该继续声称有作品）。混合页面保留源的 `total`。

**「雷蒙影视 | 🍚哆啦(XBPQ)」整个影视库没有封面，根因是懒加载图片：真封面在 `data-url` 里，而 `src` 是加载占位图。** 真实卡片是 `<img class="b-lazy" src=".../img/load.gif" data-url="<真封面>">`——**这套主题靠 JS 在卡片滚入视口时才把属性换上去，而抓取页面永远不会执行那段脚本**，所以只读 `src` 就得到 146 张一模一样的 `load.gif`。这个源的配置里 `图片` 又是个**没有 `&&` 的字面 URL**（不是 marker），所以那条路也不成立。修法是新增 `lazy_cover_url`：先读 `data-url`/`data-src`/`data-original` 等懒加载属性，**并显式识别并拒绝占位图**（`load.gif`/`loading.gif`/`placeholder`/`blank.gif`…），最后才回落到普通 `src`（多数源的真封面就在 `src`，不能因为这次修复把它们丢掉）。**实测线上：0/146 → 146/146 封面**。**拒绝占位图而不是照用**是有意的：卡片显示自己的「暂无海报」状态，比显示一个永远转不完的加载动画要好。

**这两处修复都用真实浏览器复验过（真实构建产物 + 伪造 Tauri 桥，喂入 Rust 层现在真正产出的形状）。** XBPQ 网格：**3 张海报 `complete: true`、`naturalWidth: 281`、179×268 布局正确、`anyLoadGif: false`**。切到「采集集合」再选「电影片」（即 `t=1` 那条路径）：界面显示 **「0 部 / 未检索到内容」**，`anyFolderName: false`，**控制台零错误**——截图里那 56 个假作品一个都没出现。

**第三个源的问题是「剧集地址是播放页，而流在 iframe 里」——需要下钻一层，且那个 iframe 要 Referer。** 修好解析后，29 集的地址全是 `?action=get&p=N` 这种**播放页**（`is_episode_link` 会把它们全部拒绝，因为它们既不含 `/play/` 也不含 `.m3u8`），而页面自己**不含任何媒体地址**，唯一的 `<iframe>` 指向 `us-m3u8.urldwz.com/index.php/play/2179.html`，**真正的 `.m3u8` 在那一层**。**关键实测：那个 iframe 不带 Referer 返回 404、带上嵌它的页面作 Referer 返回 200**——所以下钻时必须发 `Referer`，那正是浏览器会发的、也正是「预测播放器会拿到什么」该发的。**下钻只做一层且封顶 3 个 frame**：这些页面混着广告 frame，而超时是**每 frame 10 秒且循环是串行的**，不封顶就会让一集等上一分钟。修完实测两个真实剧集页各自解析到**不同的**真实清单（`ea5032c5` / `896047f8`），并且解析出的流**不需要 Referer 也能取**（清单和分片都 200）。

**又一次「先证明前提成立」救了我：我用 Python 逐行转写 Rust 的 `candidate_urls` 时得出「扫描器一个候选都找不到」，差点据此去改一个没坏的函数。** 原因是 **Rust 的 `html[start..].find(..)` 返回相对偏移，而 Python 的 `html.find(.., start)` 返回绝对下标**——差了 `start`，切片全是垃圾，于是「0 个候选」。**改成用应用自己的 Rust 代码跑真实页面后，结论反过来了：4 个候选、正确的 `.m3u8`。** 这也是本轮把诊断做成**临时 Rust 测试**而不是 Python 转写的原因；诊断跑完已全部删除。

**用 `Select` 前必须先读 `SelectTrigger`——三个 bug 都是没读它造成的。** ① `SelectTrigger` **自己就会渲染一个 chevron**（在 `SelectPrimitive.Icon` 里），我又塞了一个子节点，于是控件画出**两个箭头**并撑破 28px 的盒子。② 我把 trigger 的内容换成裸箭头时**丢掉了 `SelectValue`**，而 `SelectContent` 默认的 `item-aligned` 定位**需要测量 `SelectValue` 节点**才能把菜单压在 trigger 上——节点不在，Radix 无从测量，菜单**永远不出现**。正确写法是：不画箭头（让 primitive 自己出），保留 `SelectValue`，并把隐藏**写在 trigger 上**（见下条）。③ **`SelectValue` 会把 `className` 整个丢掉**——它 `const { className, style, children, ...valueProps } = props` 之后**从不转发**这两个，所以 `sr-only` 从未到达 DOM（实测该节点 `getAttribute("class")` 是 `null`，且构建产物里没有任何 `sr-only` 规则匹配它）。更糟的是**无子节点的 `SelectValue` 会让 Radix 把选中项的文本 portal 进它**，于是箭头按钮里真的渲染出「全部测速（320）」，被基类 `line-clamp-1` 裁成 **10×16px 的一格**——用户看到的就是「全」这一个残字紧贴箭头。修法是**从 trigger 经 `data-slot` 去管它**（`*:data-[slot=select-value]:sr-only`，`data-slot` 是 Radix 保留的，基类本来就用同一手法）；`sr-only` 的 `position:absolute` + 1px 盒子既不可见**又仍然可测量**，所以 `item-aligned` 照常把菜单压在 trigger 上（实测菜单 161px 宽、完全在视口内、紧贴 trigger）。**不能用 `display:none`**：那样 `getBoundingClientRect` 归零，Radix 的 `valueNodeRect` 塌掉，菜单会被丢到窗口边缘。**这套变通已随 `Select` 一起删除**（见上上条），但**结论仍适用于本项目其他 `Select` 调用点**。

**「清理不可用」的卡顿是 O(被删数 × 条目数) 的嵌套扫描，实测 release 下 1979ms。** `entry_identity`（内部含 `Url::parse`，还可能解析 JSON）原本在匹配循环的最内层被调用，删 1347 条 × 1701 条 ≈ 230 万次昂贵调用；可追溯性检查是同样的形状。改为**每个条目只算一次身份**并建哈希索引后：**1979ms → 17.5ms（113 倍）**。因为这是 113 倍的改写，「更快但算错」比「慢但对」更糟，所以**用从 git 取出的原实现做了逐字节等价验证：12 组（用例 × 文本）输出完全相同**；并保留 4 条测试钉住排序规则（精确 key 优先于更早的同名匹配、无地址条目不按身份匹配、无法追溯的文本不做修剪、大小写与末尾斜杠折叠）。Rust 命令同时从同步改为 `async` + `spawn_blocking`：**同步的 `#[tauri::command]` 跑在主线程上**，重写期间窗口完全无响应；为此 `AppDatabase` 的 `Mutex` 包进了 `Arc`（`spawn_blocking` 需要 `'static`）。

**批量测速的并发从 4 提到 16，依据是实测而非感觉。** 用户有几百个源，4 路时慢得不可接受。**真正会限制并发的那件事——每写一条结果就要重写整份文档——实测是 320 源 4.5ms、700 源 10.2ms**（release，`set_source_test_in_connection` 20 次取平均），而单条请求的预算分别是 15s（reqwest）与 25s（测试自身的外层上限）：数据库开销比网络低三个数量级，所以批量耗时**完全由网络决定**，而失败源要耗满超时，于是总时长取决于「能有多少个超时同时挂着」。16 而不是「全部并发」是为了保住两条真实约束：一个配置里的源绝大多数在不同主机上，16 路通常就是 16 个主机各收一次请求；但仍然**有界**，所以「很多条指向同一主机」的配置不会把测速变成洪水。**随之必须改的是 `update_source_test`：它原本是同步 `#[tauri::command]`，跑在主线程上**——4 路时四个结果不可能比请求更快地撞在一起，16 路则可以，16 次写串行起来在 700 源文档上约 160ms，会整段卡住事件循环。已按 `remove_sources` 的先例改成 `async` + `spawn_blocking`（`AppDatabase` 的 `Arc<Mutex<_>>` 正是为这件事准备的）。实测真实构建产物：并发峰值 **16**。

**「清理不可用」在测速期间禁用，且保留在屏幕上而不是隐藏。** 正在跑的测速**就是制造可清理源的东西**——每次失败都会关掉一个源并把它计入这个数字，所以运行中这个计数在光标底下往上跳，它背后的集合仍在变。此时点下去等于确认一次「规模和内容都没看过」的删除。守卫用的是与旁边「全部测速」**同一个 `testingKeys`**（单行测试也会一并禁用两者，而不是让相邻两个按钮一个禁一个不禁）。**注意 `title` 必须挂在包裹的 `span` 上而不是按钮上**：禁用的 `Button` 带 `disabled:pointer-events-none`，永远不是 hover 目标，挂在按钮上的 `title` 是永远读不到的标记（实测 `pointerEvents: none`、`cursor: default`、`opacity: 0.5`，点击也不会弹出确认框；结果落定后自动恢复可点）。

**源列表图标被压扁的根因是 flex item 默认 `flex-shrink: 1`，而 `size-8` 只管住宽高、管不住收缩。** 图标盒与地址行是同一行的两个 flex item，地址行带 `min-w-0` 会吸收挤压——**没有 `shrink-0` 时图标盒也一起被挤**：高度保持 32px、宽度塌到约 20px，就是用户看到的「很扁」。**为什么只有部分行出现**：只有地址长到溢出该列的行才会施加这个压力，所以它看起来像随机发生。**A/B 实测（同一页面、运行时摘掉 `shrink-0`）**：摘掉后 20 个图标全部变成 20.05–21.33px 宽（高度仍 32），加回后全部 32×32——**度量本身能区分两种状态，结论才成立**；只测「现在是 32×32」是证明不了任何事的（列不紧张时修不修都是 32）。

**分体按钮改用 shadcn 的 `ButtonGroup`，不再手写接缝。** 用户要求「有没有已经做好的组件」。`ButtonGroup` 的水平变体正是这个控件，而且它内建一条我手写时不会想到的规则：`has-[select[aria-hidden=true]:last-child]:[&>[data-slot=select-trigger]:last-of-type]:rounded-r-md`——**Radix 的 `Select` 会在 trigger 之后渲染一个隐藏的原生 `<select>`，所以 trigger 并不是 `:last-child`**，写成 `:last-child` 的圆角规则会静默失效、右半边角一直是直角。`ButtonGroup` 只统一**几何**（圆角、共享边、focus 层级）不统一**涂装**，所以 trigger 的 border/background 仍要覆盖成 outline 那套，否则一个形状两种灰。实测：flush 间隙 0.04px、两半背景一致、内角 0px/外角 6px、单箭头、`SelectValue` 1×1 不可见。

**「取消测速」根本没有停下来——用户说的完全属实，而且它有两层原因，只修一层都不够。** ① 前端只是**停止等待**：请求仍在 Rust 里跑到自己的 15s/25s 上限。② 更糟的是批量的每条请求**从不检查取消标记就落库**（`handleTestSource` 有这个检查，批量路径漏了），所以被放弃的请求照样 `updateSourceTest`、照样重写整份文档——**列表在「测速已取消」之后还在变**。修法需要前后端配合：新增 `test_runs.rs` 的 `TestRunRegistry`（按 run id 的 `AtomicBool`，与 `MediaStreamRegistry` 同构），三个测试命令都改成 `tokio::select!` 把取消与超时并列——**关键是 `select!` 会 drop 掉输的那一支，而 drop 才会真正关闭 socket**；前端每次批量生成一个 run id，取消时调 `cancel_source_test`，并**在写库前检查哨兵值**（后端返回 `__moseek_cancelled__`，单行测试也一并接入）。**实测真实构建产物**：取消后后端收到 1 个 run id、**16 个在飞请求全部被丢弃**、**取消后写入次数为 0**、run 标记被释放、UI 立刻恢复。`Cargo.toml` 的 tokio 因此需要 `macros` + `rt`（`select!` 是宏）。

**「localStorage 配额」错误的根因不是配置太大，而且它把浏览器的问题说成了配置的问题。** 用户导入 `http://xmbjm.fh4u.org/dc.txt` 时看到 `解析成功，但保存失败：... exceeded the quota`，标题却是**「需要修正配置」**。**先证伪了最像的那个解释**：真实取回该地址（54 个条目、35 个可达、11 份是真配置）→ 合并 **602 个源**，走**本项目自己的解析器 + store 自己的 `partialize`** 实测 **695 KB / 5120 KB 配额（14%）**——**远没到上限**。真正的问题是**异常从 `setState` 里逃出来**：zustand 的 `persist` 在 `setState` 内同步写 localStorage，写失败就把异常抛给调用方，于是「数据库已经存好了」被报成「保存失败」。修法是 `persist-storage.ts` 的**配额容错存储**：写不下时**降级而不是失败**——先整体写；被拒则**丢掉文档载荷（`rawConfig`/`normalizedConfig`/`sources`）保留其余**（这三个 SQLite 才是权威，镜像丢了不影响配置；主题/视图/筛选/收藏没有别处可存，必须留）；再不行就静默放弃，**绝不把已经成功的操作报成失败**。`saveParseError` 同时改成对配额情形说真话（标题「浏览器存储已满」并说明配置已保存）。**实测真实浏览器**：先用 filler 把存储填到**镜像连多 1 个字符都写不进去**（这次的前提是真的），再触发一次真实的 store 写入——镜像 **170399 → 588 字节**、`rawConfig`/`sources` 消失、`theme`/`activeView` 保留、**零未捕获异常、零配额 toast**。**注意这次验证绕了三次弯路，值得记**：前两次「通过」其实什么都没证明——一次是 filler 根本没造成压力（`fullWriteRefused: false`），一次是**替换同尺寸的值会先释放旧字节**所以照样写得进去；**配额只在载荷增长时才咬人**，而导入大配置正是增长场景。**必须先证明前提成立（镜像无法再增长），结论才有意义。**


**jsdom 无法虚拟化，这一点决定了设计。** 实测：jsdom 里 500px 高的滚动容器 `clientHeight` 是 **0**，且本项目的 `ResizeObserver` 桩**从不触发回调**。所以按测量驱动的虚拟列表在 jsdom 里会**一行都不渲染**，把现有每条表格断言都变成「找不到行」，而其实什么都没坏。因此回退是显式的、且是**真实测量而非 `typeof window` 判断**：`hasLayoutEngine()` 插入一个 10px 元素再读回来，没有布局引擎时整表渲染——这正是测试拿到的结果，也是 ~130 条既有表格测试原样通过的原因；并有一条测试断言该探针在 jsdom 下返回 false，防止它被悄悄反转。

**一条关于测试本身的教训：用永不 resolve 的 mock 时，`waitFor` 会被饿死。** 批量测速的测试里 `waitFor(() => expect(pending.length).toBeGreaterThan(1))` 实测耗时 **20 秒**（测试因此超时失败），而 `pending` 是同步就填好的普通数组、断言本身根本不需要等。**元素已经在 DOM 里时就用同步断言**，`waitFor` 只在真的需要等待时用。同理，那条依赖开发者本机数据库的配额测试已改为**按实测尺寸合成文档**——用户把文档从 1701 源换成 351 源后，它就因为与代码无关的原因失败了。

**有些直播在网页上能放、在本软件放不出来——是「两个故障」，只修一个都不行。** 用户给的 `https://live.ottiptv.cc/douyu/431460` 实测返回 `301 → …550.flv`，该地址再 `302`、最终 `200` 且 **`Content-Type: video/x-flv`**，响应体开头是 `46 4c 56 01`（`FLV\x01`）——**它根本不是 HLS**。故障一：`usesHlsPipeline` 对所有直播频道都返回 true，于是 FLV 被交给 hls.js，而 hls.js 会把它当播放列表解析并报 `manifestLoadError`。**故障二是关键的一半，也是「只做检测修不好」的原因**：`fetch_media_resource` 用 `reqwest` 的 `.timeout()` 约束**整个 body**，而直播 FLV 的 body 永不结束，所以那个 deadline 必然超时——**reqwest 把这种超时报成 `Kind::Decode`**，这正好就是用户在诊断里看到的 `error decoding response body`。实测：1MiB 预算 16441ms 后以该解码错误失败，512KiB 则 5630ms 后报体积超限；同一地址改成**只约束每次读取的间隔**后，首个 64KiB 在 **92ms** 到达。

修法是**第二条管线 + 流式传输**：`policy.rs` 把客户端 deadline 拆成 `ClientMode::{Buffered,Streaming}`（前者约束整段交换，适合会结束的文档；后者只约束读取间隙），并加 `fetch_media_prefix`（取有界前缀后主动断开，正是嗅探容器所需）与 `open_media_response`；`resolver.rs` 加纯字节判定的 `classify_media_container`（FLV magic、MPEG-TS `0x47` 步进、`#EXTM3U`、HTML，**Content-Type 只在前缀无结论时作参考**——本项目已知发布方会误标，例如把 JPEG 报成 `image/x-ms-bmp`）、`probe_media_container`、以及走 Tauri Channel 的 `stream_media_resource`/`cancel_media_stream`。前端加 `media-pipeline.ts`（纯函数）与 mpegts.js 管线 + `TauriFlvLoader`（由 Rust channel 喂数据，而不是让 webview 直接抓——这些主机不能指望 CORS，且 Rust 才能让请求走本项目的 URL/请求头/重定向策略）。`live-view.tsx` 的 player key 改为**解析后的管线字符串**：原本是布尔值，会把 FLV 与 native 键成同一个，切换时不会重建播放器。

**端到端已实测（真实浏览器 + 真实频道）**：mpegts.js `isSupported: true`，`MEDIA_INFO` 报告 `avc1.64001e,mp4a.40.2`（H.264 High 3.0 / 640×360 / 25fps + AAC 48kHz），video 元素 `readyState 4`、`currentTime 1.51s`、缓冲 **9.48s**、**解码出 31 帧**、**零错误**。另用 Node 解析该流自身的 FLV tag 独立确认编解码为 **AVC/H.264（codec 7）+ AAC（10）**，即 mpegts.js 原生支持的组合。**「检测对了」不等于「能放」，这一步必须真机验证。**

**并发改动的教训（代价真实）**：FLV 那批改动在**未提交状态**留在工作区时，我为了隔离跑门禁执行了 `git stash push --keep-index --include-untracked`，**把另一位作者正在改的文件从它脚下移走了**——`--include-untracked` 正是它两个新文件消失的原因。它从 `stash@{0}` 完整恢复（我事后逐字节比对确认无损失），但**两条改动线并行时，正确做法是让各自提交，而不是把别人的在制品挪走**；即使要隔离，也应先问、或干脆不跑那部分门禁。

**导入远程配置时，地址返回的不一定是配置。** 实测用户给的十个地址，只有四个是「`application/json` 的普通 JSON」，其余是：图片里藏配置（饭太硬：JPEG 图片在 2401 字节结束，之后 8 字节 + `**` + base64 的 JSON——这是发行方的伪装手法，浏览器打开是图、客户端读图片之后是配置）、HTML 落地页（王二小、嗷呜，该地址**根本没有配置**）、`//` 注释开头的 JSON（老刘备、小盒子单仓）、**发布方自己写坏的 JSON**（肥猫：两个 key 少了左引号，写成 `ext": {`）、404（VOX）、**多仓订阅列表**（小盒子多仓 / 拾光多仓 / 挺好分享多仓：`{"urls":[…]}` 列的是**别的**配置地址）、以及 JSON 后面被追加了 HTML 页脚（拾光多仓）。字节层的解包在 `src-tauri/src/config/decode.rs`（图片格式靠 magic number 识别，按各自的结束标记切分；JPEG 的 `FFD9` 从**后往前**找，因为它可能出现在载荷里，取第一个会把配置截断），文本层的判别在 `src/features/config/config-source.ts`（有 JSON5 解析器、测试便宜）。**两边分工是有意的：不让任何一边重复实现另一边已有的东西。**

`fetch_text` 原本用 `String::from_utf8`，**遇到 GBK 直接拒绝**——那是在把「我们猜错了编码」说成「文件有问题」。现在先试 UTF-8（GB18030 几乎能解码任何字节序列，先试它会把好好的 UTF-8 变成乱码），再按 BOM 试 UTF-16，最后 GB18030 / Big5。

**「修正」按钮修不了发布方的笔误，现在能了。** 肥猫的文件有两个 key 写成 `ext": {`（少了左引号），`repairConfigText` 新增这条修正：只匹配**行首的裸标识符紧跟 `":`**——这个形状在合法 JSON 里不可能出现，所以不会弄坏本来正确的文档。**这条修正必须排在「转义字符串内换行」之前，顺序是承重的**：先转义会改写那一行，导致两个坏 key 只剩一个能匹配、文档仍然解析不了、只是错误换到了新的一行——**这正是用户报的「点了修正也没修好」**。三条测试锁住它（一个坏 key、**两个坏 key**（真实形状，也是能抓到顺序问题的那条）、以及正确文档必须原样通过），变异验证两个方向都被抓到。

**「多仓」不是错误，是用户想要的东西之一。** 识别成列表后弹选择器让用户挑一个导入，而不是报「缺少 sites」。判据刻意收窄：只认**顶层** `urls` 数组、且元素是带 `url` 的对象——`urls` 在普通配置里也常见（播放列表字段），顶层字符串数组也不算。**落地页要报成「这是一个网页（嗷呜接口主页）」**，报「invalid JSON at character 0」虽然属实但毫无用处。

**「采集集合」影视库的三处症状（很久才加载出来 / 封面时有时无 / 分页与总页数都已出现但一直转圈）是同一个决定的代价：列表与封面补取被串成两个请求后才回答。** 实测该源（`http://zhangqun1818.serv00.net/cj/cjjh.php`）：**`ac=list` 是 5 KiB / 1.5–4.3 s 且 0/20 封面、0/20 线路；`ac=detail` 是 406 KiB / 12.8–28.3 s 且 20/20 两者都有**（`ids=` 不能减负，仍是 406 KiB/15–19 s；`limit` 被源忽略，恒返回 20 条）。一次真实运行里详情用了 **15459 ms**，正好越过 `Buffered` 客户端 15 s 的**整段交换**截止线——**所以「封面时有时无」不是源的问题，是我们的截止时间在随机砍掉那一半**。修法是让 `browse_source` **只发一次列表请求**、先让库可用。**实测真实构建产物**（真实浏览器 + 伪造 Tauri 桥，喂入**应用自己解析器**产出的真实形状）：**840 ms 页脚「第 1 / … 页」+ 标题「读取中」+ 63 个骨架；2.4 s 20 张卡片已可用（无封面）**；页脚与总页数的诚实性见下一段。**Rust 侧线上测试**：列表 3918 ms / 0 封面 / 32 分类。**「封面该不该另外去取」是用户定下的规则，见下一段——结论是：不取。**

**封面只来自列表，绝不为封面额外发请求（用户决定，且这条优先于任何性能论据）。** 我一度把封面做成**按作品并发取**（`enrichCatalogCovers`，上限 10；实测 20 个单条请求 **6762 ms / 20-20 封面**，而整页一发 **26207 ms**，字节数几乎相同 407 863 对 406 382，首个封面约 1.1 s 到），用户明确否掉了：**「用并发去取的话，很容易造成限流，并且这种不稳定的行为还是少做，我们要的是安全可靠的行为。如果对方的列表并没有提供作品的封面图的话，那就算了。」** 这条推翻是有道理的，也已照此实现：`browse_source` 是影视库发出的**唯一**请求；`needsCoverDetails`/`enrichCatalogCovers`/`loadCoverFor`/`mergeCatalogItem` 与 `fetch_catalog_details` 全部删除；列表没给封面就显示卡片自己的「暂无海报」。**别的源不受影响**——XML CMS 的 `<pic>`、XBPQ 抓的懒加载图、JSON CMS 的 `ac=detail` 列表，封面本来就在列表里。作品的**自己的页面**打开时仍会取一次详情记录（播放需要的线路就在那里），封面在那里出现。**注意与第 9 轮的关系**：目录行不带线路的那批源，进作品时会走播放页自己的 `isDetailLoading`（「正在获取剧集…」），而不是靠目录行预填——那条路径是为此存在的，所以取消封面补取不会让空状态重新闪现。

**页脚曾经在没有数据时就宣布「第 1 / 1 页」——这正是用户说的「分页和总步数都已经出现了，但页面一直处于加载状态」。** 它读 `catalog?.pageCount ?? 1`，把一个**还没读到的结果集**写成确定的答案，而内容区同时显示骨架屏：同一屏上两句话互相矛盾，且伪造的那句更自信。修法是给目录**盖作用域戳**（源 + 关键词 + 分类）：不属于当前作用域的目录根本不显示，于是切源/换分类/翻页都不需要「先清空」也不会留下旧数字；页数未知时写 `…`；页脚显示的是**正在请求的页号**。**翻页只改页号不改作用域**，所以「第 2 / 4205 页」+ 骨架屏是诚实的「正在取第 2 页」。（Rust 侧的 `merge_catalog_page`/`should_retry_for_covers` 与随后的整页/按作品两种补取都已在用户决定后删除；那条「详情响应带 20/20 封面却带 **0** 个分类而列表带 61 个」的测量仍然有效——**任何时候都不得用详情记录整页替换列表**。）

**顺带修掉一处「探测结果取决于运气」：源测试的 playback 项原本读目录行的播放地址，而目录行在拆分后本就不带地址**，于是它会退化成「没有可识别的播放地址」。现在改为读**它自己刚刚已经取回的那次 `get_detail` 结果**（同一结果原本只用来判断「能不能解析」）——既不依赖列表补取，也不再受那 15 s 随机性影响。

**页面切换不重置视图：访问过的视图保持挂载、只隐藏（keep-alive）。** 症状是用户报的「切到别的页面再回来，之前的搜索/结果就没了，像回到主页重新加载一遍」。根因在 `App.tsx`：视图是**条件渲染**的（`{activeView === "browse" && <BrowseView/>}`），切走即**卸载**，`useState` 里的搜索词、结果、页码、选中频道、滚动位置全部销毁，于是回来和第一次进来无法区分。修法是 `ViewPane`（`src/components/view-pane.tsx`）：视图**挂载过一次就一直留着**，非活动时加 `invisible`（**不是 `hidden`**）+ `aria-hidden` + `inert`。**为什么不能用 `display:none`**：源列表的虚拟列表靠**测量视口**决定挂载多少行，而实测 `display:none` 的容器 `clientHeight` 为 **0**，虚拟列表会正确地判定「没有布局引擎」并**挂载全部行**——正是它当初要消除的那个 270 ms 卡顿。`invisible` 保留盒子，测量仍然真实。**首次进入仍然正常加载**：`visitedViews` 从 `activeView` 起步、每访问一个视图追加一个，所以启动时不会把六个视图的初始请求全部打出去（`activeView` 是被持久化的，用户上次停在电视直播就还在那里）。**播放器必须例外**：视图被留着，`MediaPlayer` 就会跟着留着，而隐藏的直播流会一直下载到进程退出——所以 `MediaPlayer` 通过 `useViewActive()` 在视图离屏时 `pause()`、回来时 `play()`（**只在原本确实在播时**才恢复，用户自己暂停的不会被导航唤醒）；管线、缓冲与进度都不拆，回来是接着放而不是重载。**实测真实构建产物 + 伪造 Tauri 桥**（真实点击导航栏）：在影视库搜索「海贼王」→ 切到电视直播 → 切回影视库，**搜索框仍是「海贼王」、结果仍是「结果：海贼王」、页脚仍是「第 1 / 7 页 搜索：「海贼王」」，且整轮 `browse_source` 调用总数为 2（搜索那次之后新增 0 次）**——只有「没有重新挂载」才会是这个数字；隐藏期间该 pane 确实带 `invisible` + `inert`；零控制台错误。**测试**：新增 `view-pane.test.tsx`（6 项，含「隐藏不是 `hidden`」「`inert` 与 `aria-hidden`」「没访问过的视图不挂载」）与 `media-player-view-active.test.tsx`（2 项，暂停/恢复、以及不唤醒用户手动暂停的播放器）；两处变异各自只让对应测试失败（把 `invisible` 改成 `hidden`、以及去掉暂停分支）。

**直播「什么也没有播放，连播放器都没有出现」的根因是：管线切换时销毁了 Plyr，而 Plyr 的 `destroy()` 会换上一个克隆，并且拒绝在同一元素上二次初始化。** 用户给的频道（`live.ottiptv.cc/douyu/4258555` → `hw3a.douyucdn2.cn/...flv`）本身完全健康：同一段流用应用自己的配置在真实浏览器里独立播放正常（`avc1.640032` 1920×1080，`playing` 触发，502 帧）。缺陷在**地址没写容器时先猜 HLS、探测回来是 FLV 再换管线**这条路径上：`plyr.destroy()` 把真实元素**留在文档外**（DOM 里只剩一个没有 `src`、`readyState` 0 的克隆，`.plyr` 数量为 0），而 mpegts.js 正把 **425 帧**解进那个被摘掉的元素——**画面在放，但不在屏幕上，播放器 UI 也从未出现**。更致命的是 Plyr 自己的源码：`setup()` 开头就是 `if (this.media.plyr) return void this.debug.warn("Target already setup")`，而**整个包里没有任何地方清掉 `media.plyr`（`destroy()` 也不清）**——所以「销毁后重建」得到的**不是一个新播放器，而是一个没有容器的僵尸实例，永远不 `ready`、也不报错**，于是 `playing` 永远不会到达界面（界面门控只认 `playing`），诊断里就一直是「等待播放」。修法因此是结构性的：**播放器属于元素，只创建一次、随组件销毁**；管线切换只换背后的库（hls.js / mpegts.js / 原生），播放器的监听器**通过 ref 派发到当前管线的事件表**（`MediaPipelineEvents`）。顺带修掉同一路径的第二处：被替换掉的管线不再把自己的失败结论留在屏幕上——实测那条**猜错的 HLS 会先弹 1.2 秒「无法播放当前内容」**再开始播放。**实测真实构建产物 + 伪造 Tauri 桥（含 Channel 推流，喂真实 douyu FLV）**：`.plyr` 1 个、元素在文档内且在 `.plyr` 里、`readyState 4`、画面推进（1.2 s→3.1 s，80 帧）、**全程 `无法播放当前内容` 一次都没出现**、零控制台错误、推流 1758 块 / 2.6 MB。

**收藏与足迹的空状态必须共用同一个组件，因为「居中」写错会静默失效。** 两页原本各写一套：我的收藏 `flex h-full items-center justify-center p-8`、足迹 `flex h-96 items-center justify-center`，实测空状态盒子距内容区顶部**一个 52px、一个 97px**。根因是两种都不对——**`h-full` 只在父元素有确定高度时才有意义**，而这里的父元素是滚动视口里的普通块（高度 auto），于是 `h-full` 静默失效、塌成内容盒，位置实际由那个 `p-8` 决定；`h-96` 是写死的 384px，与所在视口无关。修法是共享的 `CollectionEmpty`（`src/features/browse/collection-empty.tsx`）用 **`min-h-80`**：不依赖百分比解析的确定高度，与影视库空状态的 `min-h-64` 同一种形状。修后实测两页一致（距顶 20px、盒高 320px）。

**切页时的「中间态」根因是 `visibility` 可被后代覆盖、且会被 `transition-all` 插值——所以隐藏 pane 要用 `opacity-0` 而不是只靠 `invisible`。** 每个 `Button` 都带 Tailwind 的 `transition-all`（`transition-property: all`、150ms），而 **`visibility` 是可插值属性、任何中间值都计算为 `visible`**；`visibility` 又**可继承但可被覆盖**，所以 `visible` 的后代在 `hidden` 祖先里**真的会被绘制**。逐帧实测：确实存在「pane 已 `hidden`、其按钮仍报 `visibility: visible` 且被绘制」的帧。**试过并否掉的两条路**：祖先的 `transition-none`（**覆盖不了子元素自己的 `transition-property`**）、`[&_*]:transition-none`（**通配选择器把整个应用启动搞崩**）。最终用 `opacity-0`：**按子树整体生效且不可继承**，没有后代能覆盖它回到屏幕上；且**不影响布局**，滚动位置与虚拟列表测量全部保留（`content-visibility: hidden` 会跳过内容布局、让滚动容器塌掉，**正是这个组件要保住的东西**）。修后泄漏帧 1 → **0**。**注意 `ViewPane` 的隐藏仍必须是 `invisible` 而不是 `hidden`**——虚拟列表要靠测量盒子决定挂载行数，`display:none` 会让它挂载全部行。**测量纪律**：keep-alive 之后两页同时在 DOM 里，**任何跨页面测量都必须先限定到活动 pane**——我第一版空状态诊断正是漏了这一步，两次都量到收藏页的盒子，得出「两页完全相同」的错误结论。

**端到端实测（走真实分类器与真实解析器）**：饭太硬 **53 个源**（从一张 JPEG 里）、肥猫修好后 **41 个源**、老刘备 237 个、小盒子单仓 55 个；三个多仓分别给出 **18 / 54 / 32** 个地址供选择；王二小与嗷呜报为落地页；VOX 报为不可达。真实浏览器实测（前端部分）：多仓选择器渲染出行与「关闭」、落地页消息点名标题、肥猫的文件取回后**自动修正并显示「已自动修正：补上 N 处缺少左引号的字段名」**、普通配置载入时**不出现**修正提示、页面无溢出、控制台零错误。

**编辑自动保存，没有保存按钮。** 在「原始配置」里改任何东西，600ms 后自动写库，**文本合法与否都先保存**（校验失败只提示、不拦截）：配置是用户自己的东西，为一次校验失败丢掉整段编辑，比留下一份暂时读不懂的配置更糟。代价是**派生状态**的规则要分清：文本可解析时照常重建源列表与 normalized；**不可解析时保留上一次的派生结果**，否则一个笔误看起来就像「所有源都没了」。空文本是独立状态（表示「没有源」），不算失败。规则在 `config-autosave.ts` 的 `resolveSavePayload`。

自动保存有**两道防重复，缺一不可**：debounce effect **不依赖 `sources`**（它是保存的**结果**而非输入，依赖它会让每次保存都排下一次——实测一次编辑写了 5 次），且 `saveEditorText` 记录已写文本、同一份不重写（**失败时必须清掉这个标记**，否则一次瞬时错误会让这段文本永远存不进去）。**测试必须断言「恰好一次」**：「编辑被保存了」这种断言在死循环下照样通过。

代码模式只有一个 **「检查并修正」**（原「校验」+「自动修正」已合并）。`repairConfigText` 原本只处理语法（BOM/空白/围栏/尾分号/字符串内换行），**对类型问题一无所知**，所以会在一份根本存不进去的文档上报「未发现可自动修正的问题」；现在它还会把五个 flag 字段的字符串写法折回真正的布尔值，只动这五个名字、只认真实文件里出现的写法。**这五个名字必须共用一份名单**（`RAW_FLAG_FIELDS` in `config-schema.ts`）：它原本在 schema 与 `config-visual.ts` 各存一份，两边漂移才让编辑器把 `"true"` 写成字符串、而 schema 拒绝整份文档（`Invalid input: expected boolean, received string`，且不说是哪个字段）。

**保存会重复一个被修复过的源**（浏览器实测）：`replace_known_live_source_urls` 把直播源改成可用的绝对地址，raw 里却仍是相对路径；保存时按 base URL 解析成 `https://szyyds.cn/tv/...`，与恢复后的 `https://iptv-org.github.io/...` **不是同一个字符串**，合并按身份匹配失败就把解析出来的又**新增**一条（实测一次无关编辑让列表 26 → 29，SAO0 与 IPV6 各两份）。`mergeSourceLists` 现在在身份查不到、且**同名的未认领直播源恰好只有一个**时按 name 兜底；**匹配到 name 时必须保留「已存」的地址**，否则会把修复悄悄退回相对路径。同名有歧义时**两条都保留**，不许折叠。

`normalized_config` **只保留 6 个顶层键**（`sites`/`lives`/`parses`/`blockedFields`/`configDialect`/`schemaVersion`），**导出用的就是它**，所以 `ads`/`flags`/`doh`/`rules`/`ijk`/`hosts`/`proxy`/`wallpaper`/`warningText`/`spider`/`logo` 这 11 项**Moseek 不读取、导出也不带**（实测占原文 18% 字节）。它们只对 TVBox 客户端有意义，可在「原始配置 → 可视化 → 其他设置」一键清理。`parses` 则**必须保留**——它是播放兜底链路的一环（地址是播放页而非媒体文件时由 Rust `resolve_playback` 使用），但每次解析**按文件顺序最多试 12 个**，重复地址会白占名额，可用「去掉重复地址」清理。

删除源时**按身份（`api + ext`）匹配原文条目，不按 `key`**：raw 与源列表的 `key` 是两套独立生成、且已经分叉的命名空间（无 key 的条目被解析器编号为 `live-1`，被合并后缀成 `-2`，两边零重叠），按 `key` 匹配会让删除漏掉原文，用户看到的就是「删了但原始配置里还在」。身份相同时**先比 key、再比 name，每个原文条目最多被认领一次**（身份并不唯一：`xgapp` 与 `骑骑影院` 就是同一 `api + ext`）。原文里「列表早已没有」的残留也会一并清理，但只在列表确实描述着这份原文时才做。**合并不得为没有 `key` 的条目生成 key**——那会把 keyless site 的 `capability` 从 `invalid` 静默升级为 `supported`（`classifySource` 的 `hasRequiredFields` 读原始 `key`），等于让导入把不可用的源变成可执行。
