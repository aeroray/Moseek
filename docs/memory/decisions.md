# Decisions

- Package manager: pnpm.
- Frontend foundation: React + Vite + TypeScript.
- Desktop foundation: Tauri 2 with Rust commands reserved for network access, parsing, storage, and playback resolution.
- UI direction: a dense content operations console with coral brand accents, blue primary actions, semantic capability status colors, IBM Plex Sans for interface text, and Space Grotesk for display values.
- MVP support boundary: ordinary CMS APIs, basic live sources, HTTP parsing endpoints, and explicit diagnostics; remote JAR, spider, Drpy JS, unsupported CSP adapters, and private protocols remain non-executable.
- Vite watcher ignores `src-tauri/**` because Windows file locks in Rust build artifacts can otherwise terminate the frontend dev server with `EBUSY`.
- Tauri uses the checked-in `src-tauri/icons/icon.svg` as the source for generated platform icons; the current bundle is disabled until installer packaging is configured.
- Phase 3 ordinary CMS support uses Rust reqwest commands for common `ac=list` and `ac=detail` JSON APIs, normalizing list/detail/play-line fields into the shared `VodItem` model; unavailable remote data stays an explicit empty/error state.
- Phase 4 media playback uses Plyr 3.8 with hls.js for HLS and native video for MP4. Progress, movie favorites, and live-channel favorites persist in the frontend store; live M3U/TXT/JSON parsing and XMLTV/JSON EPG parsing remain behind Rust commands with explicit empty/error states.
- External playback is user-triggered through `tauri-plugin-opener` and only accepts HTTP/HTTPS URLs. CMS episode URLs and live stream URLs are rejected when they use dangerous, localhost, private-network, or unsupported protocols.
- Phase 5 uses a transparent adapter registry: ordinary HTTP/type-3 CMS and live sources use built-in adapters; HTTP parser support is partial; Drpy JS, XBPQ, CSP extensions, remote JAR, spider, and private protocols are represented as blocked or needs-adapter entries and are never executed.
- JSON configuration surfaces use CodeMirror 6 with the project font token; import and raw configuration views share one editor component with bounded internal scrolling.
- The application is library-first: the obsolete overview and top header were removed, navigation remains in the sidebar, and theme selection lives in Settings.
- Configuration management uses multiple named documents with one active document at a time; normalized source snapshots and enablement state are scoped to the document so identical source keys cannot collide across imported configurations.
- Safe site dispatch uses Rust adapters for type 0 XML HTTP, type 1 JSON HTTP, and restricted type 4 HTTP-extension scalar parameters; type 3 Spider, remote JAR, and remote script paths remain blocked. All remote fetches and playback URLs pass through the shared HTTP/HTTPS policy gate with bounded responses and redirects disabled.
- The movie library only includes enabled fully supported ordinary CMS sources whose real probe returns canonical movie content; partial, parser, and blocked sources do not expose a test action, while fully supported live sources use the live probe and remain outside the movie library. Static adapter capability alone never grants library eligibility. Probe status, counts, timing, and message persist per configuration document, while generic JSON payloads without primary `vod_*` fields remain outside the library.
- Source identity is unique within each configuration: duplicate imported `key` values receive deterministic `-2`, `-3`, etc. suffixes with warnings, and persisted snapshots normalize duplicate keys when loaded.
- Kitty/CatVod root arrays, `data`, and source metadata normalize into the shared model; JS contracts remain blocked, while only public HTTP GET parse services may be attempted after direct media URL checks.
- Phase 2 declarative HTML sources use bounded CSS selectors, public HTTP fetches, and explicit scalar parameters/headers; browser automation stays outside the main process, and the optional sniffer companion is loopback-only with returned media URLs revalidated.
- Phase 3 starts with a standalone `moseek-script-runtime` QuickJS-NG JSONL prototype; it has no filesystem, shell, DOM, fetch, or host network APIs, and remote JS/JAR/Spider sources remain blocked until sidecar packaging, trust, and host API policies are implemented.
- Phase 3 now packages the QuickJS runtime as a Tauri sidecar; scripts can request only explicitly allowlisted public `http_get` calls through the main process policy, while Settings exposes a manual local-script lab and imported remote scripts remain blocked.
- The sidecar runtime has a 20-second total execution deadline and a 16-second per-request host-call deadline; nested Cargo targets are ignored while standalone Cargo lockfiles remain trackable.
- Local script archives are stored separately from imported config documents, deduplicated by SHA-256, disabled on import, and soft-deleted with an explicit undo path; archive execution requires an enabled archive ID.
- JS/CatVod sources only become executable when explicitly bound to a local `scriptArchiveId`; bound sources route getHome/getSearch/getDetail/parseIframe through the sidecar and CatVod normalizer, while unbound remote JS remains blocked.
- CatVod bindings call getCategory independently, preserve parseIframe headers for HLS playback, and normalize named export functions; full module imports and DOM remain out of scope for the current sidecar.
- Script archives may carry only validated User-Agent, Referer, and Cookie headers; archive listings expose names only, and host HTTP calls still pass through the shared network policy.
- Cookie values are stored in the Windows native credential store through `keyring`; SQLite keeps only non-sensitive headers and a `hasCookie` marker, with startup migration for legacy plaintext Cookie fields.
- Script ES modules use an explicit in-memory `modules` map; the QuickJS loader has no filesystem, network, or implicit module resolution. This preserves import compatibility without expanding sidecar authority.
- Script archive soft deletion remains reversible; permanent deletion requires a disabled archive and removes its Windows credential-store entry before deleting SQLite content. This prevents active credentials from being removed accidentally.
- Script executions return and persist redacted diagnostics: phase, duration, host-only HTTP details, error class, and timeout/credential flags. Full URLs, query strings, Cookie values, and response bodies are excluded from the log contract.
- Network policy streams bounded responses, rejects additional hop-by-hop headers, and pins each public DNS resolution in the reqwest client. This reduces memory exhaustion and DNS-rebinding risk while preserving public HTTP/HTTPS access.
- Rust application code is organized by boundary: shared models, `config/` storage and commands, `db/` initialization and migrations, and `script_runtime/` execution versus archive lifecycle. Tauri command names remain unchanged.
- Frontend config input is capped at 10 MiB, source toggles are serialized per document/source, and the root UI has a recoverable Error Boundary. These limits protect parsing and prevent stale async state from overwriting a switched configuration.
- The configuration center distinguishes adapter registration from actual source execution: source rows show their resolved adapter and status, while the adapter matrix reports current-source counts and supports filtering by enabled, partial, pending, or blocked state. This prevents “recognized” from being mistaken for “executable.”
- HTTP parsing is fully supported within a bounded contract: public HTTP/HTTPS GET or JSON POST parser services, validated playback URLs, bounded request/response bodies, and no private protocols. Local CatVod scripts are fully supported after explicit archive binding and enablement across category, home, search, detail, and iframe entry points.
- Configuration documents persist the remote source base URL; legacy documents with relative live paths expose an explicit repair action that resolves relative API/EPG URLs transactionally and refreshes live-source capability state. The app never guesses a local file's remote origin.
- For the legacy configuration fingerprint matching `huanghundeye/tjson`, the original relative live files were verified as removed; automatic recovery uses verified public compatibility lists (`my-tv1/tvv/live.txt` for general TXT and `fanmingming/live/tv/m3u/ipv6.m3u` for IPv6 M3U), only after successful content validation.
- The live workspace always renders its source selector, group list, channel list, preview, and EPG regions, including when no live source is enabled or a source returns an empty catalog. Multiple enabled live sources are selected explicitly instead of implicitly using the first source.
- Live catalog parsing does not certify stream playback: embedded HLS remains dependent on the upstream manifest/segment response and browser media policy. Player diagnostics distinguish manifest, level, and fragment failures and include upstream HTTP status codes when available.
- Live channel parsing aggregates same-channel M3U/TXT records by group plus stable ID/name after removing quality suffixes such as `@HD`, `@SD`, and `(1080p)`. The original URLs remain as ordered `streamUrls`; the UI attempts at most three variants before surfacing the final playback error.
- The local SAO0 source previously pointed at a dead `my-tv1/tvv` list whose CCTV1 routes returned 502/timeouts. It was migrated to `https://iptv-org.github.io/iptv/countries/cn.m3u`; CCTV1's 720p manifest and first MPEG-TS segment were verified with HTTP 200, and startup recovery knows this replacement for future legacy documents.
- Tauri HLS playback uses a custom hls.js loader backed by the Rust `fetch_media_resource` command. This keeps remote manifest, key, and segment requests behind the existing public-URL, header, redirect, DNS, and response-size policy instead of relying on third-party CORS headers; browser preview keeps its direct-request limitation.
- The Tauri hls.js loader omits HTTP Range when hls.js supplies the default fragment offsets `0/0`; real byte ranges use hls.js's exclusive `rangeEnd` converted to the inclusive HTTP end offset. Sending the default as `bytes=0-0` truncates ordinary fragments and produces a black live player.
- Live HLS playback uses a live-edge start position, bounded live buffering, autoplay with muted fallback, and live-only controls without VOD progress/duration UI. Fatal fragment load, parse, and buffer-append errors first refresh the live window before the channel-level variant fallback is attempted.
- Live playback does not expose transient `loading`, `ready`, `paused`, or `playing` states in the live workspace. Autoplay begins only after Plyr is ready and the first fragment is buffered; a startup watchdog and bounded manifest reload handle stalled windows in the background, while only a final channel failure reaches the diagnostic alert.
- The live `MediaPlayer` session is kept mounted across channel URL changes; one Plyr instance and one HLS instance switch sources through the existing media element instead of remounting from a React key. The Tauri loader rejects HTTP 200 bodies that are not `#EXTM3U` before hls.js parsing, avoiding misleading `manifestParsingError` reports for HTML, JSON, or FLV responses.
- Live loading remains visible until the media element emits `playing`, not merely when an HLS fragment is buffered. HLS follows the standard `loadSource` then `attachMedia` initialization order; later channel switches use the same instance's `loadSource/startLoad` path without a manual detach/attach cycle, which avoids a black MediaSource after loading.
- Live startup also uses the native `video.play()` promise with bounded exponential retries and source-version guards. A successful play request clears initial loading even if a WebView delays `playing`; `waiting`/`stalled` re-enable it, and five failed attempts become a final diagnostic instead of an infinite spinner.
- Live metadata from public IPTV playlists preserves the source channel and group names after whitespace normalization; the UI keeps the original text and handles readability through layout, truncation, and spacing rather than maintaining a translation table.
- The black live screen was caused by the Tauri CSP: `default-src 'self' ipc: http://ipc.localhost` also governs `worker-src`, so the blob-URL transmuxer worker that hls.js injects (`enableWorker`) was refused. Chromium reports that refusal asynchronously, so hls.js's synchronous `try/catch` inline fallback never runs; its `onWorkerError` only clears `config.enableWorker` and emits a non-fatal `internalException`, which the player ignored. No fragment was ever transmuxed, so no `FRAG_BUFFERED` ever fired, `video.play()` was never attempted, and the surface stayed black until the 10s startup watchdog expired. The CSP now allows `worker-src 'self' blob:`, and the player treats a `demuxerWorker` internal exception as a recoverable failure by rebuilding one HLS instance with `enableWorker: false` before reporting a diagnostic.
- `worker-src` must be listed explicitly in the Tauri CSP for any blob-URL worker. `'self'` does not cover `blob:` workers, and a synchronous-throw assumption is unsafe: verify worker startup by behaviour, not by constructor success.
- Live group ids keep non-ASCII group names distinct: `slug` still lowercases ASCII alphanumerics, but appends a stable FNV-1a suffix when the name is not pure ASCII, so CJK groups no longer collapse into one empty `group_id`.
- Rust incremental compilation is disabled for the dev/test profiles in `src-tauri/Cargo.toml`. Windows real-time antivirus scanning (observed with Huorong HIPS on this machine) intermittently denies writes inside `target/debug/incremental`, and rustc panics with an ICE (`encode_metadata`) instead of degrading when it cannot write incremental metadata. A full crate rebuild costs seconds, and the cache had grown past 7 GB with orphaned `*-working` directories from interrupted builds. Clearing `target/debug/incremental` plus this profile setting removes the failure mode; no MSVC or SDK paths are hardcoded in the repo.
- Playback failures are now observable instead of silently black. `MediaPlayer` renders a short generic overlay on the player surface (with a retry action) and streams a `MediaDiagnosticSnapshot` through `onDiagnostic`: resolved environment probe, media-element state, pipeline state, and a bounded event timeline of hls.js/Plyr lifecycle and error events. `MediaDiagnosticPanel` renders that snapshot below the player with a copyable plain-text report, so a black screen always comes with a stated reason.
- The environment probe deliberately starts a throwaway blob-URL worker. That is the only reliable way to tell whether the CSP permits hls.js's injected transmuxer worker, because Chromium reports the refusal asynchronously and `new Worker()` still succeeds.
- Radix `ScrollArea` defaults to `type="hover"`, so its scrollbar is not mounted at all while the pointer is elsewhere. The diagnostic timeline keeps that default rather than forcing a permanently visible scrollbar; scroll regions that must advertise themselves can pass `type="always"` or `"auto"` explicitly. This applies to every `ScrollArea` in the app, including the live channel list and the configuration lists.
- `MediaPlayer` must not construct Plyr or hls.js synchronously inside its effect. Plyr wraps the `<video>` element in its own DOM and hls.js attaches a MediaSource to it, so neither survives being built twice on the same element. React StrictMode mounts, unmounts and remounts effects in development, which constructed both libraries twice and left the player DOM torn down: the live workspace showed a black surface with a spinner, no `play`/`playing` events ever reached the player state, and playback never started even though the media element could reach `readyState 4`. Initialisation is therefore deferred by one macrotask that the unmount cancels, so it runs exactly once per real mount; restarts and retries still rebuild the pipeline synchronously.
- Playback diagnostics are the primary evidence for live failures: the event timeline plus the environment probe distinguish a blocked transmuxer worker, a dead upstream, a decoder gap, and a stalled pipeline without needing a debugger.
- hls.js reports every manifest problem as `manifestLoadError`, which is useless on its own. The diagnostic timeline therefore records `response.code`, `response.text`, `data.error.message`, and `reason`, because the Tauri loader forwards its own failure text on `response.text`; `policy.rs` walks the reqwest cause chain so the text names the underlying reason instead of only "error sending request". Failure copy distinguishes an upstream rejection (HTTP 401/403), a peer that closes the connection before responding, and a 200 response that is not an HLS playlist. The previous "不允许跨域" hint was removed: the desktop runtime proxies media through Rust, so CORS never applies.
- Error copy and the hls.js error description live in `media-diagnostics.ts` rather than the `MediaPlayer` component. They are pure formatting, and keeping them there lets them be unit tested without importing Plyr, which needs `window.matchMedia` that the jsdom test setup does not provide.
- A live source test probes the first channel's manifest, because fetching the catalog only proves the list is reachable. Public IPTV lists routinely contain dead, carrier-locked, or non-HLS entries, so the `playback` operation now requests one manifest through the shared policy gate, bounded to 8 seconds and 512 KiB, and requires the body to start with `#EXTM3U` (a leading BOM is tolerated). The source `status` stays catalog-driven: one dead sample must not mark a whole source failed. Instead the probe result appears as the `playback` operation and appends a warning to the source message when it fails.
- The channel probe follows redirects, matching the media path, via a separate `fetch_text_following_redirects` entry point. `fetch_text` keeps redirects disabled on purpose for catalog, EPG, and configuration fetches, but a probe whose job is to predict playback must not report a policy limit as a dead channel: the first IPV6 channel answers `302` with a session token and the followed URL then returns `403`, which is what the player actually experiences. The zero-redirect case now reports "returned a redirect (HTTP 3xx), policy does not follow redirects" instead of the misleading "redirect limit exceeded", since no hop was ever attempted.
- The Tauri media loader normalises an upstream HTTP status into `LoaderError.code` by parsing it out of the message text, and `formatHlsError` applies the same extraction when only text is available. Reporting `code: 0` for every loader-originated failure hid the status from both the diagnostic timeline and the user-facing hint, so a `403 Forbidden` was described as "the address may be dead" while the timeline next to it quoted the full status. Rejection, a peer that closes the connection, and a non-playlist 200 are three different problems and must not share one sentence.
- The configuration import dialog's draft sync depends only on `activeConfigId` and `rawConfig`, never on the base URL. Remote import sets `configBaseUrl` and loads the fetched text into `importText` in the same batch; an effect that also ran on a base URL change then overwrote `importText` with the active document's `raw_config`, so "解析配置" saved a byte-identical copy of the document that was already open while the user believed the remote configuration had been imported. Local file import was unaffected because `await file.text()` resolves after that effect. Any effect that resets an editor draft must key off the document identity and its stored content, not off derived values such as the resolved base URL.
- That rule lives in `config-drafts.ts` as `shouldResetDrafts` and is unit tested, rather than being an entry in a dependency array. A dependency array cannot express "this input must be ignored", nothing fails when the entry is added back, and no linter flags it. The test was validated by mutation: re-adding the base URL to the comparison makes exactly that case fail.
- Importing a configuration first asks whether the user already has it, and the decision stays with the user: `find_config_duplicate` reports the closest stored document and the dialog offers 跳过 or 继续导入. Text equality is not enough — the case that matters is a configuration that was imported and then trimmed by hand, so re-importing the untouched original produces different text while the source key sets reveal that one contains the other. Detection therefore matches on identical text, then on either source set containing the other, then on the same import address, and reports both source counts so the user can see which side was trimmed. Matching is deliberately generous because the user is asked rather than blocked: a false positive costs one click, while a missed match silently duplicates a configuration.
- Site and live `ext` are coerced identically. `RawSiteSchema.ext` already turned an object into JSON text, but `RawLiveSchema.ext` used the plain text rule, so a single live entry carrying `{"sp":"Huya"}` — a common CatVod marker — failed validation for the entire configuration. The two sections must not drift apart on the same field.
- Parse failures name the field when there is no line to point at. Syntax errors carry a line and column, but schema mismatches carry only a Zod path, so the dialog showed "Invalid input: expected string, received object" with no indication of which of hundreds of entries was wrong. `ParseIssue.path` is now surfaced as `（字段 lives.5.ext）`.
- A redirect whose `Location` is empty or resolves back to the current URL fails immediately instead of spinning to the redirect budget. `Url::join("")` returns the base URL, so such a response previously exhausted the hop limit and was reported as "too many redirects" although only one hop was ever attempted; it now reports that the redirect does not point anywhere new.
- `usesHlsPipeline` decides the pipeline and treats an explicit `mp4` as never HLS, even on a live channel. A live channel that pointed at a 51 MB mp4 behind a redirecting endpoint was pushed through hls.js, which fetched it as a manifest and failed on the size limit instead of playing it. Because hls.js and the native element need separate players, the live workspace keys the player on the resolved pipeline so switching between the two kinds rebuilds it; switching URLs within one kind still reuses the mounted player.
- Playlist requests carry a much smaller response budget than media fragments (1 MiB versus 16 MiB), because a manifest is a few kilobytes. Without it a non-HLS address could stream megabytes into memory before failing with a size limit rather than "this is not a playlist".
- `src/test-setup.ts` stubs `window.matchMedia`, which jsdom lacks and Plyr reads while its module is evaluated. Without it any test importing the player fails during import rather than in an assertion.
- The video element does not set `crossOrigin`. Setting it makes the element demand CORS headers from the media host, which can only break the native path (a live mp4 or a VOD file) and buys nothing here: nothing reads pixels back through canvas, `captureStream`, or WebAudio, and the HLS path feeds the element from a same-origin MediaSource blob. The removal is safe either way for hosts that do send `Access-Control-Allow-Origin`, and necessary for hosts that do not.
- Live buffering is tuned for jittery public sources: `liveSyncDurationCount: 3`, `liveMaxLatencyDurationCount: 10`, `maxBufferLength: 30`. The cushion a live player can build is bounded by its start position, because it can only buffer from where playback begins up to the live edge, so raising `maxBufferLength` alone does nothing for a short playlist window; starting one fragment further back is the change that actually buys resilience. The buffer cap is kept above the start offset and the latency cap above that, so neither ever forces a mid-playback catch-up seek. Measured basis: a 1080p channel needed ~8.3 Mbps (5.19 MB per 5-second fragment) while its server delivered 3.5–15.3 Mbps from an unrelated network, so the shortfall is upstream and only a deeper cushion can smooth it. The cost is roughly one fragment of extra startup latency.
- HLS diagnostic events keep the full stream URL on screen because locating a failing segment requires it. This is an ephemeral in-app panel and is not persisted, unlike the redacted script-runtime execution log contract.
